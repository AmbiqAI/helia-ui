import Callout from '@ambiqai/helia-ui/astro/Callout';

`heliaStarlight()` is how a Starlight site adopts the theme. It does two
things: it splices the package stylesheets into `customCss` in the order the
cascade depends on, and it installs the shell components that carry no site
vocabulary, which is the theme menu, the mobile menu toggle, and the footer.

```js
import starlight from '@astrojs/starlight';
import { heliaStarlight } from '@ambiqai/helia-ui/starlight';

starlight({
  customCss: ['./src/styles/tailwind.css'],
  plugins: [
    heliaStarlight({
      footer: {
        links: [{ label: 'GitHub', href: 'https://github.com/AmbiqAI' }],
        tagline: 'One line under the logo.',
        logo: 'ambiq',
      },
    }),
  ],
});
```

## Options

| Option                     | Type                        | Default    | Effect                                                                                                                                              |
| -------------------------- | --------------------------- | ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| `styles`                   | `boolean`                   | `true`     | Splices the four package stylesheets into `customCss`. `false` leaves `customCss` untouched, and the site loads them itself.                        |
| `accent`                   | product id                  | undefined  | The product identity color, as `data-helia-accent` on the document element. See [Product accent](#product-accent).                                  |
| `shell.themeSelect`        | `boolean`                   | `true`     | Installs the `ThemeSelect` override: the theme menu with its three choices.                                                                         |
| `shell.mobileMenuToggle`   | `boolean`                   | `true`     | Installs the `MobileMenuToggle` override.                                                                                                           |
| `shell.footer`             | `boolean`                   | `true`     | Installs the `Footer` override, which renders the brand row and the pagination.                                                                     |
| `footer.links`             | `{ label, href }[]`         | `[]`       | Navigation shown on the right of the footer's brand row.                                                                                            |
| `footer.tagline`           | `string`                    | undefined  | One line printed under the logo.                                                                                                                    |
| `footer.logo`              | `'ambiq' \| false`          | `'ambiq'`  | `false` drops the brand lockup and renders the tagline on its own.                                                                                  |
| `header`                   | `object`                    | unset      | Installs the `Header` override: the site name as text at the top-left, the links, search, and the theme menu. Unset, Starlight's own header stands. |
| `header.title`             | `string`                    | site title | The name at the top-left. It links to the site root.                                                                                                |
| `header.links`             | `{ label, href, match? }[]` | `[]`       | The sections beside the name. A link is current when the path starts with its `href`; `match` is the prefix to use instead.                         |
| `header.search`            | `boolean`                   | `true`     | Starlight's search trigger.                                                                                                                         |
| `header.themeToggle`       | `boolean`                   | `true`     | The package theme menu. Off anyway when `shell.themeSelect` is `false`.                                                                             |
| `sidebar`                  | `'docs' \| 'always'`        | `'docs'`   | `'always'` keeps the left sidebar on every page at desktop widths, a `template: splash` landing page included.                                      |
| `shell.head`               | `boolean`                   | `true`     | Installs the `Head` override: the brand font preload and the per-page discoverability tags.                                                         |
| `code`                     | `boolean`                   | `true`     | Themes Expressive Code onto the package surface. `false` leaves Starlight's code frame alone.                                                       |
| `discoverability`          | `object \| false`           | `{}`       | Search-engine and agent metadata. `false` switches the lot off; see [Discoverability](/helia-ui/starlight-plugin/discoverability/).                 |
| `discoverability.ogImage`  | `boolean`                   | `true`     | Per-page Open Graph card at `<route>/og.svg`, with the `og:image` and `twitter:image` tags that point at it.                                        |
| `discoverability.jsonLd`   | `boolean`                   | `true`     | `WebSite` and `Organization` on the home page, `TechArticle` elsewhere, and a `BreadcrumbList` from the sidebar path.                               |
| `discoverability.markdown` | `boolean`                   | `true`     | `<route>/index.md` renditions and the `alternate` link that points at them.                                                                         |
| `discoverability.llms`     | `boolean`                   | `true`     | `llms.txt`, `llms-full.txt`, and `content-index.json` at the site root.                                                                             |

## The product top bar

A product site puts its own name at the top-left, as text, with its sections
beside it. That is the `header` option, and it installs a `Header` override in
place of Starlight's:

```js
heliaStarlight({
  header: {
    title: 'heliaCORE',
    links: [
      { label: 'Getting started', href: '/heliaCORE/getting-started/' },
      { label: 'Guides', href: '/heliaCORE/guides/' },
      { label: 'API', href: '/heliaCORE/api/' },
    ],
  },
});
```

An `href` is a path on the site, written the way a footer link is: with the
site's `base` on the front, since the plugin does not prefix it for you. A link
is current when the page's path starts with its `href`, so a section stays lit
on the pages under it; `match` names a different prefix for a section whose
pages do not live under its link. A link to the site root is current on the
root alone.

Search and the theme menu sit at the end of the bar, and either can be dropped
with `header.search: false` or `header.themeToggle: false`. What Starlight
draws there by default and this bar does not is the social icon row: a site
that wants those links keeps them by naming them in `links`.

Below `62rem` the links give way to a button that opens the left sidebar, which
is where a narrow screen reads the navigation from. The button is the one entry
point to it, because the plugin's `MobileMenuToggle` override takes Starlight's
own button off the frame.

## Keeping the sidebar on a landing page

Starlight gives a `template: splash` page no sidebar, which is right for a hub
landing page and wrong for a product site: a reader who arrives on a product's
landing page should be able to see the rest of the product from it. Set
`sidebar: 'always'` and every page keeps the left sidebar at desktop widths,
the landing page included. Narrow screens are untouched: the sidebar stays
off-canvas there, as it is on a documentation page.

```js
heliaStarlight({ sidebar: 'always' });
```

The plugin does this with a route middleware rather than a component override.
Starlight decides a page has no sidebar from its template, and one flag on the
route carries that decision to the page shell, to the frame, and to the layout
widths; the middleware sets the flag back, so the sidebar is Starlight's own
and the widths follow it. This site sets the option, and
[Landing page example](/helia-ui/starlight-plugin/landing-example/) is what it
looks like.

## Product accent

`--helia-product-accent` is the one color a site gets to call its own: the
accent word in a `Hero`, an accent `Badge`, the outline on a primary action.
Without an accent it resolves to slate, which is a site with no identity color
rather than a site with a neutral one.

`accent` names a product the package already holds a color for. The plugin puts
that id on the document element as `data-helia-accent`, and `semantic.css`
derives the accent from it, so the palette stays in the package and the site
writes no CSS.

```js
heliaStarlight({ accent: 'helia-core' });
```

The ids are `helia-aot`, `helia-core`, `helia-dsp`, `helia-edge`, `helia-ml`,
`helia-profiler`, `helia-rt`, `kit-compression`, `kit-heart`, `kit-physio`,
`kit-sleep`, `kit-sound`, and `kit-vision`. Anything else fails the build rather
than falling back quietly.

<Callout tone="note" title="What the attribute costs">
  The attribute is set from the inline script the `Head` override emits, which
  is the only scope a component rendered inside `&lt;head&gt;` can reach. It
  needs `shell.head` left installed, and with scripting off the accent stays
  slate. A page that carries several products puts `data-helia-accent` on each
  subtree itself; the derivation is the same.
</Callout>

## Stylesheet order is the contract

The four sheets the plugin injects are `tokens.css`, `semantic.css`,
`recipes.css`, and `starlight.css`, in that order. They go after the leading
Tailwind roots in your `customCss` and before everything else:

```
./src/styles/tailwind.css       your Tailwind entry, which imports
                                @ambiqai/helia-ui/starlight-tailwind.css
@ambiqai/helia-ui/tokens.css    injected
@ambiqai/helia-ui/semantic.css  injected
@ambiqai/helia-ui/recipes.css   injected
@ambiqai/helia-ui/starlight.css injected
./src/styles/site.css           yours
```

Two properties depend on that position. The package sheets are unlayered, so
they outrank every cascade layer the Tailwind entry declares, which is what
keeps the tokens authoritative over the Starlight Tailwind compat package. And
the site's own sheet lands last, so a page-specific override needs no extra
specificity to win.

The plugin finds the insertion point by treating any leading `customCss` entry
whose filename matches `tailwind*.css` as a Tailwind root. If your entry is
named something else, put it first and name it accordingly, or set
`styles: false` and order the sheets yourself.

## Overrides you already set win

A Starlight plugin's `updateConfig` shallow-merges over the site's config, so
an array or a map written by a plugin would replace the site's rather than add
to it. Both values this plugin touches are read back from the config and merged
by hand instead. `customCss` is spliced, not replaced, and a shell override is
installed only under a key the site left alone.

<Callout tone="note" title="Keeping your own Footer">
  Name `Footer` in Starlight's `components` map and the plugin will not touch
  it, with no need to set `shell.footer: false`. The same holds for
  `ThemeSelect` and `MobileMenuToggle`. Use `shell.*: false` when you want
  Starlight's stock component back rather than one of your own.
</Callout>

## How options reach the shell

Starlight hands nothing to a component override, so the resolved options reach
the Footer through the module graph. The plugin adds a small Astro integration
that serves them from the virtual module `virtual:helia-ui/starlight-config`,
which is how Starlight itself does this and keeps the values build-time
constants rather than runtime lookups. Nothing outside the package should
import that module: it is an implementation detail of the shell components, and
its shape is not part of the export map.

## Discoverability

The plugin also emits the search-engine and agent metadata every HELIA site
needs, so no site authors its own.
[Discoverability](/helia-ui/starlight-plugin/discoverability/) states the
contract: what lands in the head, which artifacts land at the site root, and how
a page opts out of the description rule.
